## javaScript中的字符

由于历史原因，JavaScript中的字符虽然采用的也是Unicode字符集，但是却只支持一种编码方式：**UCS-2**！

那么上面我们已经了解过了UTF-16和UCS-2的关系：**UCS-2使用2个字节表示0-65536（基本平面）范围内的字符，而UTF-16是UCS-2的超集，它除了用2个字节来表示基本平面字符外，还使用4个字节来表示其余16个辅助平面的字符。**

### 编码导致的问题

#### 1. 对所有字符都当作2个字节处理，那么如果出现4个字节的字符会出现怎样的结果？

| 字符 | Unicode码点 | Unicode编码 | javaScript编码 |  ES6编码  |
| :--: | :---------: | :---------: | :------------: | :-------: |
|  𝐆   |   119814    |  0x01D406   |    \u1D406     | \u{1D406} |

```javascript
var char = '𝐆'
char.length === 2 // true
char === '\u1D406' // false
String.fromCharCode(119814) // "퐆"
char.charCodeAt(0) // 55349
char === '\uD835\uDC06' // true
```

> js中进制转换
>
> 55349..toString(16).toUpperCase() === 'D835'
>
> parseInt('D835', 16) === 55349

这样的结果肯定是不对的

* 首先这个字符的长度应该是1而不是2
* 其次JavaScript把4个字节的字符拆成了2个字符来处理肯定也是不对的

#### 2. ECMAScript 6的出现解决了上述的问题：

```javascript
var char = '𝐆'
Array.from(char).length // 1
char === '\u{1D406}' // true
String.fromCodePoint(119814) // "𝐆"
char.codePointAt(0) // 119814
char === '\u{1D406}' // true
```

## HTML中的字符

### 浏览器解析HTML文件时使用的编码方式

1. 首先根据Content-Type确定请求返回的类型为`text/html`也就是html文档，如果这个时候Content-Type后面还跟着编码方式的话，浏览器就会按照这个编码方式开始解析此html文件。**优先级最高！**

   ```http
   content-type: text/html; charset=utf-8
   ```

2. 否则，按照ASCII编码的方式对html的meta部分内容进行解析，希望可以通过charset来得到页面的编码方式和编码后的字符集。

   ```html
   <meta http-equiv="Content-Type" content="text/html" charset="utf-8" />
   <meta charset="utf-8" />
   ```

   > 这里注意⚠️
   >
   > charset虽然翻译起来表示是字符集，但是在这里它真实的表示是：字符编码方案和编码后的字符集这两种概念的组合！
   >
   > 理解起来就是，Unicode是一种字符集，但是UTF-8是Unicode的一种字符编码方案，除此之外还有UTF-16、UTF-32。而在charset里只需要用一个UTF-8就可以表示将二进制数据映射为唯一的字符的一整套算法。
   >
   > HTML中meta中的charset和HTTP中的MIME中的charset使用的是同一套标准，也就是[IANA](http://www.iana.org/assignments/character-sets/character-sets.xhtml)

3. 如果页面没有设置charset的话，那浏览器就只有靠设法扫描实际的文本，看看能否找出语言和编码的常见模式，以此推断字符编码。

### HTTP数据传输

首先，HTTP（超文本传输协议）不仅可以传输文本，还能传输图像、视频等二进制数据。

> HTTP/0.9时，客户端只能发送get请求，服务器只能回应HTML格式的字符串，不能回应别的格式。

这里我们首先可能会对上面的定义提出质疑：

**所有的数据在互联网上传输难道不都是二进制的吗？**

这里需要区分的一个概念是，数据在互联网上传输肯定都是以二进制进行传输的，但这是相对于较底层的协议来讲的。实际上在网络传输中，我们经常会分为`文本传输`、`二进制传输`。

**对于http协议来说，只有报文主体才会区分文本传输或者二进制传输！**

为什么这么说？因为http报文的首部和URI等字段必须使用ASCII编码，这也就是**为什么cookie里面只能存储ASCII码的原因**！所以只有报文主体才可以自定义各种传输内容，像普通文本、json字符串、文件。

**大家都是二进制数据的话，不管是传输方还是接收方要怎么去理解数据原本的状态呢？**

这里就出现了上述讲到的MIME了，这个东西出现的目的就是为了标识传输内容的状态，从而告诉浏览器或者服务器如何处理这些数据。最早出现于电子邮件领域，因为当时规定电子邮件只能使用ASCII字符，所以也就意味着不能使用ASCII以外的字符集、不能有图片、不能有附件。所以就有了MIME，后来被HTTP协议引入。

![image-20200618172045254](https://static.normalhamal.online/20200703232217.png)

**那么为什么要区分文本传输和二进制传输呢？全部换成二进制传输不好吗？**

这里我了解到的原因是：二进制传输不会在传输过程中处理原始数据，所以传输后得到的数据应该是完全等于原始数据的，而文本传输在传输过程中会换行符进行处理，因为我们都知道:

| 字符 | Windows | Unix | Max  |
| :--: | :-----: | :--: | :--: |
|  ↵   |  \r\n   |  \n  |  \r  |

这里顺便还引出一个另一个概念：`BASE64`

上面说到在电子邮件领域只能使用ASCII字符，所以如果我非要发送一张图片怎么办呢？这时就出现了将二进制数据转换为ASCII编码的方式：BASE64，之所以叫BASE64，正是因为它通过使用64个可打印字符（不包括'='的话）就可以组成一个字符集。

**我通过浏览器的页面发送了一个http请求，请求中包含了一串字符串放在请求体中，那么这串字符串最终会用怎样的编码方式编码并传输呢？**

那当然是浏览器用的什么编码方式解析的你的页面，那么默认发送的请求中携带的文本数据就会按照什么编码方式发送。

### `\e900`  `&#xe60c;`

是的，你可能经常在前端开发中遇到过这2类字符，那么它们到底是一种怎样的编码呢？

其实它们就是Unicode字符在css和html中的使用方式，那么你可以联想到Unicode字符在JavaScript中的使用方式是什么呢？

| Unicode字符 | JavaScript |  css  |  HTML   |
| :---------: | :--------: | :---: | :-----: |
|     我      |   \u6211   | \6211 | &#x6211 |

**那么在css或者html中直接使用Unicode编码一般发生在什么场景呢？**

字体图标！原先我们要在页面上使用图标的话可能需要一个图标一张图片或者是精灵图去做，不够灵活，我们要是能把一个个图标当作文字来处理就会非常灵活了，我们甚至可以随意对它进行大小、颜色等属性更改而只需要通过编写css代码就行了。那么原理呢就是基于WebFont了，通过使用一个个Unicode字符来对应一个个图标，当我们想要在页面上使用时就可以通过Unicode字符去引入了。

那么我们肯定不想用来表示图标的Unicode字符在某种情况下却被当作真实的字符来使用了，所以我们会把一些在Unicode中原本就不可见的或者说空白的字符来对应我们的图标。

### escape、encodeURI、encodeURIComponent

既然要讲这几个方法，那么就很有必要先提一嘴它们出现的原因：

![image-20200619113700529](https://static.normalhamal.online/20200619113705.png)

那么总结起来就是：**为了使URL在因特网上可以安全地、可读地、完整地被所有因特网协议进行传送，我们需要一种转义机制，将不安全的字符编码为安全字符、将不可见无法打印的字符转为可见字符、将非ASCII字符转为ASCII字符，再进行传输。**

**编码机制**

1. 将不安全的字符表示为一个百分号后面加上字符ASCII码的十六进制数（例如空格就会被编码为`%20`）。

2. 在URL中，有几个字符被称为**保留字符**，它们包含特殊含义。有些不在ASCII可打印字符集中。有些还会和某些因特网网关和协议产生混淆，因此不赞成使用。这些保留及受限的字符如下：

   ![image-20200622202417837](https://static.normalhamal.online/20200622202423.png)

那么现在我们再回过头来看标题的3个JavaScript函数：

那么从上面我们可以得到的信息是：

1. escape已经不被推荐使用，所以我们最好不要使用它。
2. encodeURI和encodeURIComponent的区别只有：是否对`;,/?:@&=+$#`这些字符进行转义。

第2条信息的原因可以这么理解：

当我们需要在URI中传递一个包含`;,/?:@&=+$#`里面字符的数据，例如我们需要传递一个字段为wd，值为`name=normalhamal@gmail.com&psw=123456`的query参数时：

```http
http://www.baidu.com?wd=name=normalhamal@gmail.com&psw=123456
```

如果我们使用encodeURI对它进行转义你会发现结果并不会有变化，因为：

> 假定一个URI是完整的URI，那么encodeURI不会对那些保留字符或者在URI中有特殊意思的字符（;,/?:@&=+$#）进行编码。

但是这样的结果传到后端服务器，服务器解析后得到的就是：

```http
wd: name=normalhamal@gmail.com
psw: 123456
```

而使用encodeURIComponent进行转义就可以得到：

```javascript
'http://www.baidu.com?wd=' + encodeURIComponent('name=normalhamal@gmail.com&psw=123456')
// http://www.baidu.com?wd=wd%3Dname%3Dnormalhamal%40gmail.com%26psw%3D123456
// wd: name=normalhamal@gmail.com&psw=123456
```

所以为了避免服务器收到不可预知的请求，对任何用户输入的作为URI部分的内容你都需要用encodeURIComponent进行转义。

### URI VS URL VS URN

这里稍微了解下上面3个名词的概念和区别，因为在上面的转义方法中我们可能会想，为什么是encodeURI而不是encodeURL？

每个Web服务器资源都有一个名字，这样客户端就可以说明它们感兴趣的资源是什么了。而服务器资源名就被称为统一资源标识符（Uniform Resource Identifier，URI）。

URI表示资源的形式有2种，就是上面的URL和URN了，那么为什么在我们的印象中经常搞混URI和URL呢？这是因为现在几乎所有的URI都是URL了，那么URN又是怎样的形式呢？

URN是作为特定内容的唯一名称使用的，与目前资源所在地无关。使用这些与位置无关的URN，就可以将资源四处搬移。比如，不管因特网标准文档RFC 2141位于何处，都可以用下列URN来命名：

`Urn:ietf:rfc:2141`

为了更有效地工作，这样的一种表现形式需要一个支撑架构来解析资源的位置，而此类架构的缺乏导致URN被采用的进度延缓，所以URN仍然处于试验阶段，还未大范围使用。
