## EditorConfig

**EditorConfig**在我看来就是一个配置统一的文件编码以及格式的工具。

从官方的**wiki**说明上我们可以看到，目前它仅仅只支持8个可配置属性，但是未来它可能支持更多。

一个有效的**EditorConfig**配置文件应该以`.editorconfig`命名并且如下设置属性：

|           属性           |              描述              |                           可能的值                           |
| :----------------------: | :----------------------------: | :----------------------------------------------------------: |
|       indent_style       |         代码缩进的样式         |                          tab、space                          |
|       indent_size        |           缩进的大小           |                       tab、an integer                        |
|        tab_width         |  一个简单的制表符（tab）宽度   | a positive integer (defaults indent_size when indent_size is a number) |
|       end_of_line        |             换行符             |                         lf、crlf、cr                         |
|         charset          |         文件的字符编码         |         latin1、utf-8、utf-16be、utf-16le、utf-8-bom         |
| trim_trailing_whitespace |      表示行末是否允许空格      |                         true、false                          |
|   insert_final_newline   |  表示文件结尾是否插入一个空行  |                         true、false                          |
|     max_line_length      | 在达到指定字符数量之后强制换行 |                    positive integers、off                    |

对于文件的通配符匹配规则（**INI like format**）如下：

|    通配符    |                说明                 |
| :----------: | :---------------------------------: |
|      *       |        匹配任意字符串，除了/        |
|      **      |           匹配任意字符串            |
|      ?       |            匹配任意字符             |
|    [name]    |  匹配`name`中任意单个字符，比如`a`  |
|   [!name]    | 匹配非`name`中任意单个字符，比如`b` |
| {s1，s2，s3} |      匹配任意一个给出的字符串       |
| {num1..num2} |  匹配`num1`到`num2`中任意一个整数   |

一个规范的配置如下（从Vue项目中copy过来的）：

```ini .editorconfig
# https://editorconfig.org

# top-most EditorConfig file
root = true

[*]
charset = utf-8
indent_style = space
indent_size = 2
end_of_line = lf
insert_final_newline = true
trim_trailing_whitespace = true

[*.md]
insert_final_newline = false
trim_trailing_whitespace = false
```

### root属性

关于这个root属性有什么用，官方网站上给出的是：

> root:  special property that should be specified at the top of the file outside of any sections. Set to true to stop .editorconfig files search on current file.
>
> root: 应该被特别地放置在文件的最上面的特殊属性。如果设置为true就会停止在当前文件下搜索.editorconfig文件。（中式英语翻译）

反正不管怎么翻译，最后你会发现其实它真正的用法都是没办法从这行话中得到的。。。

最后我在微软的**Visual Studio 2017**[操作指南](https://docs.microsoft.com/zh-cn/visualstudio/ide/create-portable-custom-editor-options?view=vs-2017#override-editorconfig-settings)上得到了答案，并且经过自己测试得出以下解释：

**`.editorConfig` 文件设置应用于同级目录以及任何子目录中的文件**

**上一级目录下的`.editorConfig`文件默认情况下会影响并替代任何子目录中的`.editorConfig`文件中没有显示设置的属性**。

假设我们现在有如下目录结构：

![](http://cdn.normalhamal.online/20190124121532.png)

最外层的`.editorConfig`的配置如下：

```ini .editorconfig
[*]
indent_style = space
indent_size = 4
insert_final_newline = true
```

**subdir**下面的`.editorconfig`的配置如下：

```ini subdir/.editorconfig
[*]
indent_style = space
indent_size = 8
```

那么对于**subdir**目录下的`sub.txt`文件来说，它将会被应用到的编码格式就将会是这样的：

```ini subdir/.editorconfig
[*]
indent_style = space
indent_size = 8
# extends outer .editorconfig file
insert_final_newline = true
```

**如果你想确保外层`.editorconfig`文件不会影响你这一级甚至更下一级的文件编码，你可以在这一级的`.editorconfig`文件最上面中添加属性`root = true`**

比如还是上面举例一样的的文件目录结构：

最外层的`.editorConfig`的配置如下：

```ini .editorconfig
[*]
indent_style = space
indent_size = 4
insert_final_newline = true
```

**subdir**下面的`.editorconfig`的配置如下：

```ini subdir/.editorconfig
root = true

[*]
indent_style = space
indent_size = 8
```

那么对于**subdir**目录下的`sub.txt`文件来说，它将会被应用到的编码格式就将会是这样的：

```ini subdir/.editorconfig
root = true

[*]
indent_style = space
indent_size = 8
```

是的，当你设置`root = true`之后，你的`.editorconfig`文件就不会再受外层配置文件的影响。

## ESLint

这个就不用多说了，Javascript代码规范和错误检查工具。它既可以配置一些代码质量上的规范，也可以配置代码的风格。你可以[点击这里](https://cn.eslint.org/docs/rules/#stylistic-issues)查看ESLint可配置的代码风格。

一般地，我们会在项目根目录创建一个`.eslintrc.*`文件来作为配置文件，或者你可以直接在`package.json`文件里的`eslintConfig`字段指定配置。

详细配置请移步[ESLint中文网](https://cn.eslint.org/)

## Prettier

**Prettier**是什么？

它是一个可以完全统一你的代码风格的工具，在之前，**Javascript**官方一直没有一个严格的代码风格，虽然业界有一些比较流行的代码风格，比如[Airbnb](http://airbnb.io/javascript/)和[Standard](https://standardjs.com/)，但是你得学习它们的文档并投入使用，这可能会花费掉你一点点时间。

现在有了**Prettier**，它有着自己的规则来将你的代码重新格式化，虽然你可能会认为可配置的代码风格工具才是最好的，就像**ESLint**，但是，当你遵从流行的代码风格反而需要不停地**fix**你的**ESLint Error**的时候，你会发现，只需要保存文件，工具便自动帮你格式化好代码并统一风格是有多么的好了。

那么总结下它的好处，那就是以下几点：

1.  不用修复**ESLint**报告的风格问题。
2.  保存文件的时候自动统一风格。
3.  不用学习其他人的代码风格。
4.  不用再去争论规则的对与错。

**Prettier**一共有四种配置方式：

1.  根目录创建`.prettierrc `文件，能够写入YML、JSON的配置格式，并且支持`.yaml/.yml/.json/.js`后缀.
2.  根目录创建`.prettier.config.js `文件或者`.prettierrc.js`，并对外export一个对象.
3.  在`package.json`中新建`prettier`属性.
4.  根目录创建`.prettierrc.toml` 文件，后缀`.toml`是必须要的.

简单的JSON配置就像这样：

```json .prettierrc.json
{
  "trailingComma": "es5", //数组 对象尾随逗号 [arr, ] { obj, }
  "tabWidth": 4,
  "semi": false, //是否在每一句后面加分号
  "singleQuote": true //使用单引号
}
```

详细配置请移步[Prettier官网配置](https://prettier.io/docs/en/configuration.html)

## 最终组合版

**EditorConfig + ESLint + Prettier**

目录结构：

```

.eslintignore
.editorconfig
.prettierrc.json
.eslintrc.json
package.json
```

安装命令：

```bash
$ npm install --save-dev --save-exact prettier eslint
```

### 集成**Prettier**到**ESLint**

集成**Prettier**到**ESLint**上有两种不同的方法：

#### 1.  配合ESLint检测代码风格

安装插件：

```bash
$ npm i -D eslint-plugin-prettier
```

eslint-plugin-prettier插件会调用prettier对你的代码风格进行检查，其原理是先使用prettier对你的代码进行格式化，然后与格式化之前的代码进行对比，如果过出现了不一致，这个地方就会被prettier进行标记。

然后在`.eslintrc.json`中配置

```json .eslintrc.json
{
  "plugins": ["prettier"],
  "rules": {
    "prettier/prettier": "error"
  }
}
```

#### 2.  关闭ESLint的代码格式化规则

如果你只想要禁用和ESLint发生矛盾的规则，同时保持其它Prettier不关心的规则。那么最简单的方法就是使用`eslint-config-prettier`。

```bash
$ npm i -D eslint-config-prettier
```

然后在`.eslintrc.json`中配置（添加eslint-config-prettier到extends数组中，把它放在最后来确保它有机会重写所有规则）

```json .eslintrc.json
{
  "extends": ["prettier"]
}
```

#### 3. Use both

如果你想以上两种方法都配合着使用的话，你只需要先安装它们：

```bash
$ npm i -D eslint-plugin-prettier eslint-config-prettier
```

然后在`.eslintrc.json`中配置

```json .eslintrc.json
{
  "extends": ["plugin:prettier/recommended"]
}
```

## git check

虽然有了前面的各种规范工具，但是你还是应该在提交代码前再次确认一遍。我们假设你已经在你的`package.json`文件中定义了以下字段：

```json package.json
{
    "scripts": {
        "eslint": "eslint --fix app.js ./*/*.js",
        "prettier": "prettier --write ./**",
        "test": "npm run prettier && npm run eslint"
    }
}
```

那么你就需要在提交你的代码之前至少运行一次`npm run test`来确保你这次的提交代码是规范的。你可以通过下面的方式来帮助你自动完成这一操作（仅针对**前端**推荐了后面2个插件）：

### git hooks

这个就很好说明了，所谓的**hooks**（钩子）也就是在某件特定的事件发生之前或者之后执行的脚本或者程序的。

你打开你的项目的根目录，找到`.git`文件夹，然后打开`.git`下面的`hooks`文件夹：

![](https://cdn.normalhamal.online/20190124170542.png)

以上这些文件就是所谓的钩子文件，你可以把对应的文件后缀`.sample`去掉，然后打开编写你的shell脚本，它会在你执行对应的git命令的前后自动执行。

比如你可以修改文件`pre-commit.sample`为`pre-commit`，然后往里面写入：

```shell pre-commit
npm run test
```

### husky

介绍就不用介绍了，反正就是一个可以省去你改hooks文件并且集成配置在`package.json`的一个工具吧。

下载安装

```bash
$ npm i -D husky
```

配置

```json package.json
{
  "scripts": {
    "precommit": "npm run test"
  }
}
```

### pre-commit

同上介绍，但是看名字你就知道它只是提供在**commit**之前执行脚本的功能，如果你还需要在**push**之前的钩子功能，你可以安装[pre-push](https://www.npmjs.com/package/pre-push)来配合你的需求。

下载安装

```bash
$ npm i -D pre-commit
```

配置

```json package.json
{
    "scripts": {
        "eslint": "eslint --fix app.js ./*/*.js",
        "prettier": "prettier --write ./**",
        "test": "npm run prettier && npm run eslint"
    },
    "pre-commit": "test"
}
```
